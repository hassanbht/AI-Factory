# 1. Mandatory Production Gaps to Fix First

Before adding new features, address the real gaps discovered during Phase 17.4.9.

## 1.1 Worker Degradation Observability

Phase 17.4.9 discovered:

> OrchestrationRunWorker's poll loop does not update IWorkerHealthCoordinator or operational metrics correctly when transient dependency failures occur.

Implement complete worker lifecycle reporting.

Required lifecycle states:

```text
Starting
Ready
Degraded
Stopping
Faulted
```

Requirements:

* Consecutive transient poll failures must transition:

```text
Ready -> Degraded
```

* Successful recovery must transition:

```text
Degraded -> Ready
```

* Fatal unrecoverable failure must transition:

```text
Any -> Faulted
```

* Shutdown must transition:

```text
Starting/Ready/Degraded -> Stopping
```

When degraded:

* `worker.live` must remain present.
* `worker.ready` must be removed.
* `worker.degraded` must exist.
* Operational metrics must record degradation.
* Structured logs must include:

  * worker state
  * failure category
  * consecutive failure count
  * correlation/operation information where available

Recovery must automatically restore:

```text
worker.ready
```

and remove:

```text
worker.degraded
```

Do not require a worker restart for normal transient recovery.

---

## 1.2 Duplicate Resource Conflict Mapping

Phase 17.4.9 discovered that duplicate project slug creation correctly fails at the database level but may surface as:

```text
HTTP 500
```

This must be corrected.

Introduce a safe database constraint violation translation mechanism.

Requirements:

```text
Unique constraint violation
        ↓
Domain/Application conflict abstraction
        ↓
ConflictException
        ↓
HTTP 409 Conflict
```

Do not expose:

* SQL statements.
* database names.
* index names.
* connection strings.
* provider-specific raw exception messages.

The API response must remain RFC ProblemDetails compliant.

Example:

```json
{
  "type": "https://httpstatuses.com/409",
  "title": "Operation conflict",
  "status": 409,
  "detail": "A resource with the same unique value already exists.",
  "code": "conflict",
  "correlationId": "..."
}
```

The implementation should support SQLite and be extensible for PostgreSQL.

Do not hard-code project-specific logic inside `ApiExceptionMapper`.

The provider-specific database exception translation belongs in Infrastructure.

# 9. SQLite Backup Correctness

Do not implement backups by blindly copying a SQLite file while the database is active.

Use a SQLite-consistent backup strategy.

The backup must represent a transactionally consistent database state.

The implementation should safely handle:

```text
WAL mode
active readers
active writers
busy conditions
temporary retryable failures
```

Reuse existing:

```text
IDatabaseResiliencePolicy
```

where appropriate.

Backup failures must not crash:

```text
API
Worker
```

A failed scheduled backup should:

```text
record metrics
write structured logs
record audit event
update diagnostics
```

---

# 10. Backup Verification

A successful file creation is not enough.

Every backup should optionally be verified.

Verification should include:

1. File exists.
2. File size > 0.
3. SQLite database can be opened.
4. Integrity check succeeds.
5. Backup metadata matches expected database identity/version where possible.

Do not perform expensive verification synchronously in HTTP request paths.

Scheduled backups should run as background operations.

---

# 11. Backup Retention

Implement retention cleanup.

Requirements:

* Keep newest `RetentionCount` valid backups.
* Never delete the currently executing backup.
* Do not delete backups marked invalid until diagnostics have recorded them according to retention policy.
* Cleanup failures must not delete unrelated files.
* Backup directory operations must defend against path traversal.

Use deterministic file naming.

Example:

```text
ai-factory-2026-09-03T22-15-00Z.db
```

# 14. Restore and Disaster Recovery

Do not automatically restore production databases.

Implement a controlled restore workflow.

Recommended approach:

```text
CLI mode
```

Example:

```bash
dotnet AI.Factory.Api.dll --restore-backup <backup-id>
```

or a dedicated recovery executable if architecturally cleaner.

Requirements:

1. Restore must require explicit confirmation.
2. Restore must never silently overwrite a database.
3. The target database must be stopped/offline.
4. Backup must be verified before restore.
5. Existing database must be preserved as a pre-restore safety copy where possible.
6. Restore success must be verified using SQLite integrity validation.
7. Restore operations must generate audit and diagnostic information.

For non-interactive container environments, confirmation should require an explicit environment variable or command flag.

Example concept:

```text
--restore-confirm
```

Do not expose restore functionality through a public HTTP endpoint.
